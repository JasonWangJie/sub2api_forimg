## 优先优化一：参考图分类与本地回退

185 个参考图下载失败中，账号 33 有 86、账号 32 有 78、账号 12 有 14，其余 7 个在本机下载阶段结束。另列的参考图大小限制 4 个不包含在这 185 个中。主簇包括：

- `Reference image download failed ...`：账号 33/32 合计 101 个。
- `Reference image download exceeded its total time budget ...`：58 个。
- `reference image fetch failed ...`：账号 12 共 14 个。

两套现有分类使用 `download reference image`、`fetch reference image` 等片段，未覆盖上述词序。生产虽然配置 `passthrough_fallback_local`，但这些响应没有进入参考图重试处理。整个窗口 Gemini 任务的 `reference_retry_count` 总和为 0，任务传输模式全部仍为 hybrid，没有切到 local 的记录。OpenAI 则已有 84 个 local 模式成功任务，说明回退机制并非整体关闭。

83 个 `HTTP 502 / invalid fileData image: image URL fetch failed ... context deadline exceeded` 还有顺序问题：

1. 它们全部为 `image_to_image`，保留了远程参考图 URL 审计，最终账号 12；发生在北京时间 `2026-10-21 09:53:32` 至 `17:30:05`，不是检查当晚新增的 83 个故障。
2. Gemini Service 识别明确拉图失败后，故意把响应交给 Worker 做本地回退。
3. Worker 先执行通用 ambiguous 判断，`502 + context deadline exceeded` 提前进入 unknown，后面的参考图分支没有机会运行。83 个任务均 hybrid、参考图重试为 0；其中 72 个此前已尝试多个账号，不能写成全程没有换号。

建议统一 Service、Worker 和尝试累计使用的参考图分类，补已核实的完整错误模式；对完整响应中可信的“生成前输入图片获取失败”先做专用分类，再走通用未知兜底。继续复用持久化 local 回退、原重试预算与退避，不对所有 timeout/502 放开再次生成。结果图片下载失败、真正无响应或执行阶段不明仍保持 unknown。

83 个样本目前只确认输入拉图错误文案与代码分支，尚未独立证实上游生成与计费阶段；放行该模式前需确认它表示生成前失败，无法确认则继续保留 unknown。不能只交换判断顺序就认定重试安全。

参考图明确失败与上述 83 个 unknown 合计 268 个，约占 764 个异常的 35.1%；这是受影响样本范围，不是承诺能挽回的数量。当前没有做真实请求复现，也没有向上游核实是否计费，历史 unknown 不自动重放。

源码：[共用分类](../backend/internal/service/async_image_protocol.go#L442)、[Gemini 专用交接](../backend/internal/service/gemini_chat_completions_compat_service.go#L257)、[Worker 分类顺序](../backend/internal/handler/durable_async_image_worker.go#L643)、[Worker 参考图判断](../backend/internal/handler/durable_async_image_worker.go#L797)。

## 优先优化二：新增组合能力 422 与精确路由

生产 `.54` 的旧尺寸错误换号已经起作用：账号 26 的 `422 / image_size_not_supported` 失败审计有 104 条，涉及 100 个任务，其中 87 个任务最终成功。另有 3 个任务最终仍为旧尺寸文案 422，但都尝试过多个账号；不能只看终态认定旧修复失效。

新出现的 21 个错误均在组 11、账号 26、`gpt-image-2.5-flare` 图生图：1K 有 4 个、2K 有 17 个；全部只尝试账号 26。最早北京时间 `2026-10-23 22:17:46`，最后提交于 `23:46:25`。日志提取后的脱敏归一化字段如下（capability_errors 原位于 details）：

```json
{
  "type": "invalid_request_error",
  "code": "image_request_capability_not_supported",
  "capability_errors": ["image_model_not_supported", "image_size_not_supported"]
}
```

message 是“capability combination + model + image size”三段组合。现有分类只接受完整旧尺寸句，全等匹配不覆盖新文案；普通 typed user error 路径也未完整保存 provider code/status 到尝试审计，因此本次要结合应用日志确认结构。

建议：

1. 对已核实的新组合拒绝增加严格分类，结合 provider code、能力原因与完整文案进入有限换号；保持模型、清晰度和尺寸，不自动降级成其他模型。
2. 可另行授权，临时从已证实不兼容的精确组合中移出或降低账号 26 的路由优先级。当前组 11 / flare / 2K 还有 active 且可调度的账号 3、2、24；它们是候选，不代表已完成相同请求的兼容性验收。1K 候选需操作前另查。不要全局禁用仍有大量其他规格成功记录的账号 26。
3. 中期把兼容性和短冷却按账号×模型×清晰度保存，减少每个任务都重新发现固定能力不符。

另外 2 个 Gemini `422 / Internal error encountered` 属于“其他上游或输入错误”类别，不纳入上述 24 个能力 422，不建议泛化所有 422。

## 优先优化三：中文容量 400 进入独立退避

101 个任务最终错误为 `HTTP 400：排队等待可用账户槽位超时，当前并发已满`，均为 Gemini 账号 12；其中 96 个已尝试多个账号，只有 1 个存在容量重排记录，该记录不证明是由最终这条错误触发。不能将其写成“101 个从未换号”。

Worker 容量分类不认识该中文，普通上游重试主要识别 5xx。建议将这类明确未获得上游槽位的错误加入严格容量分类，复用当前容量重试 3 次、30–120 秒退避、jitter 和 Retry-After 上限；对相关上游容量短冷却。上游若可调整，应返回 429/503 并携带合理 Retry-After，而不是用 400 表示容量不足；503/Retry-After 语义见 [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#section-15.6.4)。

账号 12 当前已经 `schedulable=false`，本轮没有操作，也不根据当前状态推断历史关闭时间。未来恢复前应核实上游槽位与 fileData 获取问题；不靠增加本站 Worker 并发解决上游容量不足。

## 2026-10-24 本地优化实施

### 指定任务与直接换号规则

用户明确要求任务 `asyncimg_48de7444b4968293bc7a5186be50a5ba` 同类错误换号，不能同账号重试。再次只读查询确认：

- Gemini / `gemini-3-pro-image-preview`、图生图、2K、组2、账号33，提交北京时间 `2026-10-24 00:10:21`，失败于 `00:10:58`。
- HTTP400：`Reference image download exceeded its total time budget for [URL] (budgetMs=35000; reason=timeout)`；hybrid、retry_count=0，原执行只有账号33。
- 新增分类仅接受HTTP400及完整已知预算耗尽格式，要求HTTPS来源、正预算、`reason=timeout`；泛超时、附加禁止重试/安全拒绝文字、其他HTTP状态不因该规则获得重试。

OpenAI API Key/OAuth、Gemini API Key/OAuth均在私有异步路径先处理该错误，进入已有有限换号，显式 `RetryableOnSameAccount=false`。即使账号池配置HTTP400同号重试3次，调用顺序也只允许A→B，不是A→A→A。保持模型、尺寸、清晰度、参考图和既有切换预算；管理员透传优先，同步路径保持原样。

候选或切换预算耗尽后，私有Worker响应保留HTTP400和稳定内部code `async_image_reference_budget_exceeded`；Worker在参考图、容量或普通上游重试之前终止该任务，不返回同账号参考图重排循环。诊断保留原provider code、request ID、Retry-After与预算原因，来源URL整条隐藏，避免签名泄露和长URL截断分类。

还补了跨次执行的保护：若A预算耗尽后B返回503，后续Worker重排可能放宽普通历史排除；现在从完整持久 `account_attempts` 推导任务级不可重选集合，两Gateway每轮始终合并，A即使超出最近三个失败账号的窗口也不能重入。预算失败也不计入普通参考图的sticky同账号重试累计。该集合仅对当前任务生效，不全局停用账号，无数据库迁移。

### 精确内部422加入直接换渠道

原422规则只处理已知尺寸或组合能力拒绝，不能覆盖这次内部错误。本轮新增独立分类：HTTP422、完整规范化`Internal error encountered.`及按既有诊断口径得到的UNKNOWN必须同时满足；四Service凭据路径在私有异步上下文进入有限直接换号，显式禁止同账号重试，管理员透传和临时规则优先。
