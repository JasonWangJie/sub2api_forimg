本例每渠道三条是**一次调用的三个不同阶段**，不是此前同一组三条重复保存成六条的问题。典型换号会成为 `A已选择 → A已发起 → A失败 → B已选择 → B已发起 → B成功`，六条过程记录通常对应两次发送尝试，不能当六次生图或六次计费。

这样记录有三个目的：

1. 区分选中了但因并发槽、取token、请求构造或熔断而未开始发送的情况；只有“已选择”不代表调用了上游。
2. 用开始标记约束实际生成发送预算，区分一次选择和同渠道再次发送；恢复和统计不能拿所有审计行数当请求数。
3. 保留每次结果、HTTP状态、错误码、request ID和切换原因，便于追查在哪个环节失败。详细记录按阶段即时落库，不必等最终结果才留下全部过程。

三条不是固定规则：选中后未发出可能只有一条或两条，同渠道内部重试可能出现多个开始标记。因此不能将记录数简单除以3。`invocation_started` 写在统一HTTP调用入口之前，入口内仍有主机校验和客户端获取，之后还可能遇到DNS/TCP/TLS/代理错误；它表示本机开始发送尝试，不能单凭该标记证明供应商已收到、生成或收费。

实现位置：OpenAI的[选中/结果审计](../backend/internal/handler/openai_images.go)分别在261、362/422、448行；[生成调用](../backend/internal/service/openai_images.go)806行记开始、809行进入Do；[预算标记](../backend/internal/service/async_image_attempt_budget.go)62行保存 `invocation_started`；[统一HTTP入口](../backend/internal/repository/http_upstream.go)198行起。当前[任务详情](../frontend/src/features/async-image-tasks/AsyncImageTasksView.vue)434/443行分别展示生图请求次数与记录条数，683行起只统计开始标记；[中文文案](../frontend/src/i18n/locales/zh/asyncImageTasks.ts)明确使用“查看尝试记录（N条）”。

## 为什么尝试历史变成六条

[调用捕获器](../backend/internal/service/async_image_account_attempt.go)将账号选择、实际 HTTP 调用开始、成功分别作为审计记录保存。因此一次正常成功调用本来就包含三条，而不是每条都代表一次请求。

具体重复发生在结果 URL 恢复链路：

1. [结果处理器](../backend/internal/handler/async_image_result_fetch.go)在上游返回成品来源后调用 `asyncImageAttemptState(task, parent)`，把本次 capture 的三条记录合并保存到任务，然后进入 `upstream_succeeded`。
2. 它以同一个 `parent` context 调用 `resumeAsyncImageResultFetch(parent, saved, cfg)`。`saved.AccountAttempts` 已包含三条记录，但 context 中的 capture 仍包含同样的三条。
3. 下载成品后，恢复函数调用 [completeAsyncImageInvocation](../backend/internal/handler/durable_async_image_worker.go)，该函数再次调用 `asyncImageAttemptState(task, parent)`。
4. `MergeAsyncImageAccountAttempts` 直接 append，没有去重或消费已保存的 capture，故把三条变成六条。没有再次调用生成接口。

[详情页面](../frontend/src/features/async-image-tasks/AsyncImageTasksView.vue)将 `account_attempts.length` 填入“查看尝试历史（N 次）”，把审计条数表达成调用次数。[详情接口](../backend/internal/handler/async_image_task_center_handler.go)的 `AccountAttemptCount` 同样使用 `len(attempts)`，所以“尝试账号数”也会失真，尽管唯一账号列表已单独计算。

## 为什么时间线两次显示上游已完成

以 `d6793104…` 为例，真实事件如下：

| 北京时间 | 真实事件 | 状态变化 | 当前页面 |
|---|---|---|---|
| 13:32:23.376875 | `result_fetch_pending` | invoking → upstream_succeeded | 上游已完成 |
| 13:32:23.381726 | `result_fetch_attempt` | 无 | 获取生成图片 |
| 13:32:23.913106 | `upstream_succeeded` | upstream_succeeded → upstream_succeeded | 上游已完成 |
| 13:32:23.913106 | `result_fetch_completed` | 无 | 生成图片已保存 |
| 13:32:24.068542 | `storage_started` | upstream_succeeded → uploading | 上传中 |
| 13:32:24.106180 | `billing_started` | uploading → billing_pending | 等待计费 |
| 13:32:24.123756 | `task_succeeded` | billing_pending → succeeded | 已完成 |

[来源仓储](../backend/internal/repository/async_image_result_fetch.go)先持久化成品来源，记 `result_fetch_pending` 并进入 `upstream_succeeded`，保证后续只下载同一成品。下载、暂存和账务准备完成后，[最终结果仓储](../backend/internal/repository/async_image_task_repo.go)复用原成功保存逻辑，再记一个同状态的 `upstream_succeeded` 以及 `result_fetch_completed`。

详情接口优先用 `ToStatus` 覆盖 `EventType`，页面只翻译 `event.status`。已有的 `result_fetch_pending=等待获取生成图片` 文案因此没有被使用，两件不同的后处理事件显示成同名。第二条记录没有回到 invoking，也没有重新生成。

注意：事件表中的 `invocation_started` 是 Worker 取得执行权；尝试数组中的同名状态由 [调用预算](../backend/internal/service/async_image_attempt_budget.go)在真实生成 HTTP 调用前记录。两者含义不同，且本轮尝试数组存在重复，不能直接数原始行数。

### 尝试审计、预算和统计

- [审计合并](../backend/internal/service/async_image_account_attempt.go)改为幂等：按完整审计内容及非零时间戳去重，保留首次出现顺序；不同时刻的同账号调用或不同诊断字段均保留。没有可靠时间戳的旧记录不合并，避免把真实重试抹掉。
- 新审计在首次捕获时生成独立 `event_id`，随捕获器和持久记录保留。Windows时钟可能给紧邻的两次真实尝试相同时间，独立标识保证这类真实尝试不会误合并；重复保存同一捕获器则沿用同一标识。旧记录无需回填或迁移。
- [生成预算](../backend/internal/handler/async_image_runtime_resilience.go)、任务中心详情和可靠性统计采用对应去重口径；16次真实生成调用上限不变。详情读取时处理旧重复记录，不写回数据库；`account_attempt_count` 返回有效唯一账号数。
- [可靠性SQL](../backend/internal/repository/async_image_reliability_stats.go)按完整 JSON 去重，保留无时间、零时间及无效时间的旧审计；真实纳秒差异不丢失。使用有界数字检查时间格式和日期，不依赖 PG16 的 `pg_input_is_valid`，也不对任意审计时间作可能报错的 timestamptz 转换。实际验收在 PG16.14，未单独运行 PG14/15。
- 管理端把“查看尝试历史（N次）”改为“查看尝试记录（N条）”，单独显示“生图请求次数”和“尝试账号数”。请求数只数实际调用开始标记；旧任务缺少该标记时显示 `-`，空排队任务显示0。开始请求/获取图片采用进行中色，暂存完成采用成功色。

### 阶段事件和完成时间

- 新的结果恢复完成只记 `result_fetch_completed`，不再写同状态的第二个 `upstream_succeeded`。普通直接完成路径仍记录真正的上游成功事件，原有持久化、CAS、来源删除和账单准备事务保留。
- 结果最终保存保留首次 `upstream_succeeded_at`，避免把成品下载和暂存时间算入生图耗时；原值为空时才采用当前成功时间。
- 详情将 `result_fetch_pending` 显示为“等待获取生成图片”；旧任务确有 `result_fetch_completed` 时，隐藏对应的 `upstream_succeeded → upstream_succeeded` 冗余成功事件。真正的首次成功、没有完成事件的记录、重试和终态事件保留。原始数据库事件不删除。
