## 为什么会大量出现

当前[暂存仓储](../backend/internal/repository/async_image_result_fetch.go)的 `SaveAsyncImageFetchedObject` 使用：

```sql
INSERT INTO async_image_staging_objects
  (task_id,image_index,content,content_type,byte_size,checksum,width,height,expires_at)
SELECT $1,$2,$3,$4,$5,$6,$7,$8,$9
WHERE EXISTS (
  SELECT 1 FROM async_image_tasks
  WHERE task_id=$1 AND status IN ('upstream_succeeded','uploading','storage_failed')
)
ON CONFLICT(task_id,image_index) DO NOTHING;
```

`$1` 同时参与 SELECT 输出和子查询比较，原 SQL 没有显式类型，实际 PostgreSQL 解析即报 `text` 与 `character varying` 冲突。这不是账号 24、26、38 分别发生的网络故障，而是它们共同进入了有缺陷的结果 URL 持久恢复路径。

[结果处理器](../backend/internal/handler/async_image_result_fetch.go)的错误链为：

1. GET 前原子占用一次结果获取次数，最多三次。
2. 下载并校验图片成功，调用 `SaveAsyncImageFetchedObject` 保存图片字节。
3. SQL 返回错误后，代码直接要求五秒后重排，没有保存该错误事件或应用日志。
4. 下轮缺少已暂存图片，再 GET 同一 URL，再占一次次数。三个次数耗完后，下一轮直接以 `result_fetch_exhausted` 失败，覆盖了真正的数据库错误。

因此只提高下载超时、增加下载次数或换渠道不能解决这一根因。正常的第三次下载错误本会产生 `result_fetch_failed`；本次没有该事件，与“下载成功但暂存失败”的路径吻合。

固定截止时点已有 **28 个**同类失败：账号 26 为 15 个、24 为 8 个、38 为 5 个。当前进程启动后共有 29 个 `result_fetch_pending`，其中 28 个失败、1 个仍在结果获取，共记录 86 次 `result_fetch_attempt`，没有 `result_fetch_retry/failed`。这只统计进入结果来源持久恢复的分支，不表示所有生图任务失败；没有远程 URL 的输出可走其他结果处理路径。

## 修复与历史任务恢复边界

后续应优先修复 SQL 参数类型，同时记录暂存失败的独立事件和日志，避免将数据库失败无声地计入下载预算；补真实 PostgreSQL 对暂存、重复写与任务状态门的集成回归。维持原模型、图片规格及不重新生成的约束。

截至固定时点，28 条失败任务均仍保留未过期的加密结果来源，暂存图片数为零。本地来源最早在北京时间 **2026-10-31 07:36:22** 到期，最晚为 `08:58:43`；24 小时是本地来源保存期限，不是上游 URL 的有效期。此次没有解密或实测这些链接，不能承诺可追回数量。

现有[恢复后处理入口](../backend/internal/service/async_image_task_resume.go)只接受 `storage_failed/billing_failed`，不接受本次 `failed/result_fetch_exhausted`。以后抢救应提供受控的“只恢复同一结果来源”流程，维持固定账单键、原子状态和扣费幂等；不能把任务改回 queued 重生，也不能假称后台现有按钮已经支持。任何生产修复、重启或任务数据调整须按用户后续明确指令执行。

## 同时发现的独立恢复扫描错误

PostgreSQL 日志还每约 30 秒出现：

```text
ERROR: value "9223372036854775807" is out of range for type integer
```

[任务仓储](../backend/internal/repository/async_image_task_repo.go)将非正数重试上限替换为机器最大 int；amd64 为上述 64 位数值，但 SQL 与 `INTEGER` 类型的重试计数比较，两个参数被推断成 32 位 integer。[恢复扫描](../backend/internal/handler/durable_async_image_worker.go)扫描失去心跳的 invoking 任务时传入 `0,0`，触发越界，且该分支不记录应用错误。

只读 PREPARE 返回的参数类型确为 `{text[],timestamptz,integer,integer,bigint}`，只读 `SELECT 0::integer < '9223372036854775807'` 重现同一错误。该问题使“租约过期 invoking 转 execution_unknown”扫描失效；传实际 5/10 上限的后处理恢复扫描及独立的执行超时扫描仍可运行。它是另一项缺陷，不是本次结果暂存失败的直接原因，后续应独立修复和回归。

### 结果暂存及预算处理

- [结果仓储](../backend/internal/repository/async_image_result_fetch.go)逐个指定 SQL 参数类型，使用无长度的 `varchar` cast，避免显式长度转换静默截断输入。合格任务行加锁，防止与终态转换交错；同一索引、内容、校验和、尺寸、类型及维度的重复保存幂等成功，保留首次字节和来源有效期，不覆盖不同图片。
- [结果处理器](../backend/internal/handler/async_image_result_fetch.go)下载成功后，保留同一份字节，以独立 15 秒上下文最多尝试三次保存，不在这三次保存之间再 GET。保存结果不明确时回读完整字节及元数据，包含最后一次写入，确认已经落库才继续。
- 保存失败新增脱敏日志 `async_image.result_staging_save_failed` 和事件 `result_staging_save_failed`，分别记录 `download_attempt` 与 `save_attempt`。三次仍失败时，明确以 `result_staging_failed` 终结并保留加密结果来源，不再把该数据库错误静默转成下一轮下载或误报为下载预算耗尽；不准备账单、不重新生图。
- 已暂存图片仍跨 Worker 复用，原 GET 上限、模型、规格、固定账单键及后处理幂等不变。进程崩溃或数据库持续不可用、连终态都不能提交时，仍依靠原持久来源和恢复机制；不能据此承诺任何中断场景都不会再次 GET。

### 独立失联扫描修复

[任务仓储](../backend/internal/repository/async_image_task_repo.go)用 `0` 明确表示不限制重试上限，负数输入兼容归零；SQL 参数显式为 `bigint`，正常正数上限仍独立生效，显式 64 位大上限也不再被推断为 int4。失联 invoking 扫描失败新增 `async_image.stale_invocation_scan_failed` 告警，不再静默忽略。
